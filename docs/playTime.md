# Play Time: Encrypted Persistence on Windows, Linux, and macOS

## Scope and Validation Status

The launcher displays `Play Time - HHH:MM` below Change ISO, aligned with the disc metadata on the right. Hours use a minimum of three digits and can exceed 999. No play-time overlay is drawn in the game.

The Windows implementation was tested successfully by the local operator. Linux and macOS support has been prepared and reviewed statically, but has **not been compiled or executed** in those environments. This document describes implementation contracts and required validation, not a claim of completed cross-platform testing.

## Counting Contract

- Reading the total for the launcher does not create or modify the save, or generate a key.
- Timing begins immediately before emulation, after initialization succeeds. Opening and closing only the launcher does not increase the total.
- The counter measures elapsed real time using `std::chrono::steady_clock`, including boot, menus, pause, and gameplay. It is not a count of simulated frames or CPU instructions.
- Whole seconds are accumulated across sessions; formatting truncates to hours and minutes. For example, two 40-second sessions produce one displayed minute. Sub-second fractions are discarded at exit.
- A normal exit writes the new total through an `atexit` handler, including the runtime's SDL quit path using `std::exit`.
- A crash, forced termination, power loss, or POSIX signal that terminates without running exit handlers loses the current session's elapsed time. No frame-loop checkpoints are performed.
- A headless session does not record time.
- Authentication, keyring access, encryption, and file I/O happen before emulation or during shutdown, never during active frame processing.

## Platform Matrix

| Platform | Encryption and integrity | Key storage | Save location |
|---|---|---|---|
| Windows desktop | DPAPI, `CryptProtectData` / `CryptUnprotectData` | Windows user credentials; no application-managed key file | `gametime.save` beside `exPlusAlpha.exe` |
| Linux | libsodium XChaCha20-Poly1305 authenticated encryption | Secret Service through libsecret | `$XDG_DATA_HOME/PSXRecomp/<game-id>/gametime.save`, or `$HOME/.local/share/PSXRecomp/<game-id>/gametime.save` |
| macOS | libsodium XChaCha20-Poly1305 authenticated encryption | User Keychain through Security.framework | `$HOME/Library/Application Support/PSXRecomp/<game-id>/gametime.save` |

The game ID is sanitized for use as a directory component. Linux accepts only an absolute `XDG_DATA_HOME`; an unset or relative value uses the HOME fallback. An absent or invalid home directory disables persistence rather than placing a save in the current working directory. Reading the launcher total does not create directories.

The existing WindowsStore/UWP profile is outside this desktop feature's scope and reports the counter as unavailable.

## Windows Format and Compatibility

The original Windows DPAPI format is retained without migration. The encrypted payload contains `PSXTIME1` and an unsigned 64-bit little-endian second count. Optional DPAPI entropy identifies `psxrecomp/gametime/v1/<game-id>`.

The save normally depends on the same Windows user credentials and computer, with the exceptions supported by Windows profiles. Changing directories within that environment does not change the DPAPI entropy. Existing tested Windows saves remain readable.

## Linux/macOS File Format

The complete save is 64 bytes:

| Offset | Length | Contents |
|---:|---:|---|
| 0 | 8 | `PSXTIME2` format identifier |
| 8 | 24 | Fresh random XChaCha20 nonce |
| 32 | 32 | Encrypted 16-byte payload plus 16-byte authentication tag |

The plaintext payload is `PSXTIME1` followed by an unsigned 64-bit little-endian second count. Associated authenticated data binds the save to `PSXTIME2/psxrecomp/gametime/v2/<game-id>`. A fresh nonce is generated for every write.

The 32-byte encryption key is randomly generated by libsodium. It is never embedded in the executable, stored in settings.toml, or written beside the save.

### Linux Credential

The Secret Service schema is `org.psxrecomp.GameTime`, with attributes `game=<game-id>` and `version=2`. The key is stored as 64 hexadecimal characters in the default persistent collection. The session-only collection is not used.

The runtime uses asynchronous libsecret operations on a private GLib context, requesting cancellation after five seconds. A locked key store, unavailable D-Bus session, absent Secret Service provider, denied unlock, malformed key, or canceled operation disables recording. A desktop Secret Service implementation must be available and unlocked; installing libsecret alone does not supply a credentials service. The provider may request unlock or permission. No fallback key file or plaintext save is generated.

### macOS Credential

The Keychain item is a generic password with service `org.psxrecomp.GameTime.v2` and account `<game-id>`. The value is the raw 32-byte key. The application does not request synchronization through iCloud.

Access requests `kSecUseAuthenticationUIFail` and temporarily disables interaction for the legacy macOS keychain through `SecKeychainGetUserInteractionAllowed` / `SecKeychainSetUserInteractionAllowed`, restoring the previous process policy afterward. If an item needs authentication or access is denied, the counter becomes unavailable. A locked login keychain or changed code-signing identity/access policy may prevent access. These legacy interaction APIs and the authentication-UI constant are deprecated in current Apple SDKs but remain used for compatibility with the login keychain; validate this backend when upgrading SDKs. Validate access using the final signed distribution, including upgrades. Do not delete the old credential as an automatic recovery step.

## Failure, Concurrency, and Writes

- A missing save displays `000:00` without touching the key store. A key and encrypted zero-valued save may be created only when starting emulation.
- If a save already exists but its key is missing, invalid, denied, or unreadable, the runtime preserves the save and refuses to generate a replacement key for it.
- Invalid formats, wrong game identity, failed authentication, or corrupted ciphertext display `Unavailable`. Recording is disabled for that run and stderr reports the reason. Gameplay continues.
- No encryption error silently switches to plaintext.
- Windows serializes sessions with a named mutex. POSIX builds use a nonblocking advisory lock on `gametime.save.lock`; leave this small lock file in place, including after normal exit, to preserve lock identity between processes. The OS releases the lock after process termination. A second overlapping session does not record time.
- POSIX save directories are private to their owner (`0700`); newly created saves, temporary files, and lock files use `0600`. Non-regular saves, saves owned by another user, and final-component symlinks are rejected.
- Writes use a unique temporary file in the save directory, then replace the save after the encrypted data is fully written and flushed. POSIX also attempts to flush the containing directory. Failure before replacement preserves the previous save. Filesystem/device failures and sudden power loss remain subject to OS durability guarantees.
- Keys and decrypted payload buffers are cleared after use. The session key is retained in memory until normal shutdown to avoid keyring calls during gameplay.
- Save files and their temporary/lock files are excluded by the project and framework `.gitignore` files. Never include credentials or personal saves in release artifacts.

## Security Boundaries and Portability

Encryption and authentication prevent direct text editing and detect unauthenticated changes to the encrypted payload. They do not prevent a user who controls the machine and their account from accessing their own key store, modifying the executable, inspecting process memory, deleting a save, or replaying an older authentic save. There is no server-backed anti-rollback authority.

Windows DPAPI saves cannot be opened directly on Linux or macOS. Linux/macOS use the same encrypted envelope but independent credentials; moving a save alone is insufficient. Credential migration/export is not implemented. Back up the encrypted save together with the platform's supported credential backup mechanism when changing accounts or computers.

## Build and Packaging Requirements

### Windows Desktop

Link `crypt32`. No libsodium or libsecret dependency is added to Windows. Reuse the existing local build script, including `PlusAlphaProject/tools/build_s1_309_icon.ps1`; build execution remains the operator's responsibility.

### Linux

In addition to the existing SDL2/build requirements, install the development dependencies before CMake configuration:

```sh
sudo apt-get install libsodium-dev libsecret-1-dev pkg-config
```

CMake requires libsodium >= 1.0.12 and libsecret-1 through pkg-config imported targets. Missing dependencies fail configuration rather than creating an unencrypted build. The distributed binary needs matching libsodium/libsecret runtime libraries and a working desktop Secret Service provider; for Ubuntu/Debian packaging, declare the appropriate runtime package dependencies for the target release. An AppImage/other bundle must ship its shared-library dependencies while using the user's external Secret Service.

### macOS

Install the existing SDL2/build dependencies and libsodium for the target architecture:

```sh
brew install libsodium pkg-config
```

CMake finds `sodium.h` and **libsodium.a**, plus the system Security and CoreFoundation frameworks. The archive is linked statically so users do not need the builder's Homebrew libsodium dylib. Default search hints cover `/opt/homebrew` and `/usr/local`. For another prefix, provide `PSX_SODIUM_INCLUDE_DIR` and `PSX_SODIUM_STATIC_LIBRARY` explicitly. The archive must contain the requested target architecture; a universal build needs a universal archive or separate architecture builds with appropriate dependencies.

This does not replace the existing requirements for packaging SDL2, launcher assets, code signing, or notarization.

## Required Local / Platform Validation

Perform these checks independently on Windows, Linux, and macOS; CI compilation alone cannot confirm runtime credential access:

1. Open and close only the frontend: no new save or credential; an existing save's content and modification time remain unchanged.
2. Launch a game for at least 65 seconds, close normally, reopen the frontend: approximately one additional minute appears. Confirm persistence after a logout/login or restart.
3. Run two shorter sessions totaling more than one minute: retained whole seconds accumulate across sessions.
4. On a backed-up test save, change a ciphertext byte: the counter becomes unavailable and the modified file is preserved. Restore the backup afterward.
5. Make the credential store unavailable/locked or deny access: gameplay still starts, existing data is preserved, and no plaintext/key-file fallback appears.
6. Start two processes sharing a save: the second reports recording disabled; the first total is not overwritten by the second.
7. Force-terminate a session: the previously committed total remains readable, with no guarantee for the interrupted session's duration. Confirm a later normal session records correctly.
8. Test a final signed macOS application and a later signed update against the same existing Keychain item.
9. Check POSIX ownership and permissions, read-only executable installation directories, and paths containing spaces/non-ASCII characters.
10. Repeat the operator's Arcade stability test with the same renderer/settings. No frame-loop telemetry, timing/pacing, renderer, or gameplay code was changed for persistence.

## Implementation Files

- `psxrecomp/runtime/src/game_time.h`: platform-independent interface and save path selection.
- `psxrecomp/runtime/src/game_time.cpp`: existing desktop Windows DPAPI backend.
- `psxrecomp/runtime/src/game_time_posix.cpp`: Linux/macOS authenticated encryption, credential providers, POSIX persistence, and locking.
- `psxrecomp/runtime/src/main.cpp`: read-only launcher total and one session-start hook before emulation.
- `psxrecomp/runtime/runtime.cmake`: platform-scoped dependencies.
- `psxrecomp/runtime/launcher/launcher.h`, `launcher.cpp`, and `assets/launcher.rml`: existing read-only frontend display.
